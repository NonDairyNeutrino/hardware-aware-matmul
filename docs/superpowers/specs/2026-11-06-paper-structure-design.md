# The Site as a Paper: Abstract, Introduction, Methods, Results, Discussion, Conclusion

Status: design approved in conversation, 2026-11-06. Builds on the stage C site
(`2026-11-05-stage-c-site-design.md`); the playground that spec calls C3 becomes
part of the Results section here (P2).

## Goal

Give the published site the structure of a scientific paper (IMRaD plus an abstract):

| Paper section | Page | Source |
|---|---|---|
| Abstract | the landing page (`/`) | `docs/paper/abstract.md` |
| Introduction | `/introduction/` | `docs/introduction.md` (existing) |
| Methods | the five level chapters, grouped in the navigation | `docs/levels/*.md` (existing) |
| Results | `/results/`: benchmarks of each level, then the playground | `docs/paper/results.md` plus generated data |
| Discussion | `/discussion/`: the benchmarks compared | `docs/paper/discussion.md` |
| Conclusion | `/conclusion/`: summary of introduction, methods and discussion | `docs/paper/conclusion.md` |

The levels already read as Methods: each is a procedure plus its correctness
argument. The new sections are the ones that need data.

## Decisions (made with the repository owner)

| Question | Decision |
|---|---|
| Where do the Results numbers come from? | A committed **reference run** on a stated machine (native and in-browser) gives stable figures to cite; the **playground** lets each reader reproduce it on their own machine. |
| Where does the new prose live? | `docs/paper/`, rendered by the existing prose pipeline, **not** included in rustdoc (it is about the study, not the API). |
| Build order | P1 skeleton, then P2 Results (with the playground), then P3 Discussion and Conclusion. |

## Design

### Site structure

- Navigation follows paper order: Abstract (landing), Introduction, Methods (Levels
  0 to 4, grouped under one label), then Results, Discussion and Conclusion **once
  they exist**. Nothing empty is published.
- The level chapters keep their URLs. The Introduction moves from `/` to
  `/introduction/`; `/` becomes the abstract.
- Each entry of `chapters` in `site.config.mjs` gains a `section`
  (`abstract`, `introduction`, `methods`, later `results`, `discussion`,
  `conclusion`). The layout groups consecutive chapters of a section in the
  navigation. The previous/next links follow the order of `chapters`, which is the
  paper order.
- The landing page's heading is the site title; the abstract text sits under it.

### Prose and numbers

- Prose is Markdown under `docs/paper/`. The content collection pattern list gains
  `paper/*.md` explicitly; it is never `docs/**` (which also holds
  `docs/superpowers/`).
- **Numbers never appear in the Markdown.** Prose cites them with placeholders such as
  `{{speedup:simd/naive@512}}`. At build time the remark plugin fills each from a
  generated data file; **a placeholder with no matching key fails the build**, like
  an unlisted link does today. The abstract, discussion and conclusion can state
  figures without going stale or being typed by hand.
- `CLAUDE.md`'s rule "the docs deliberately contain no benchmark numbers" becomes
  "benchmark numbers appear only as generated data, never typed in prose".

### Reference run (P2)

One script produces `results.json`:

- native timings on the author's machine, from the repository's own benchmark code;
- in-browser timings (single-threaded and threaded) from headless Firefox, using the
  gates' machinery.

Each run records the CPU, thread count, build flags, matrix sizes, repeat count (the
median is reported) and the date. It is regenerated by hand, not in CI: CI machines
are too noisy to trust for timing.

### Results page (P2)

- Tables and charts per level: time, GFLOP/s and speedup against level 0, native
  against browser, and thread scaling.
- Below them, the playground ("run it on your machine"), as designed in the stage C
  spec (Web Worker, timeouts, isolation state machine with a single-threaded
  fallback).
- A note that browser timings are indicative.

### Discussion, Conclusion, Abstract (P3)

- Discussion compares the levels using generated figures: where each gain comes from,
  why scaling stops (memory bandwidth), browser against native, and the limits of the
  measurements.
- Conclusion summarises the introduction, the methods and the discussion.
- The abstract (about 150 words) is first written qualitatively in P1, then revised
  with the headline figures once the results exist.

## Plans

- **P1, skeleton:** the `section` field and grouped navigation, `docs/paper/abstract.md`
  as the landing page, the Introduction at `/introduction/`, the glob extended, the
  output checker updated, `CLAUDE.md`. Publishable on its own.
- **P2, Results:** the reference-run script and `results.json`, the placeholder
  mechanism in the plugin (with tests), the Results page, the playground (the stage C
  plan C3).
- **P3, closing sections:** Discussion, Conclusion and the final abstract, written
  last because they summarise numbers that must exist first.

## Risks and open items

- **Renaming the repository** moves the Pages address (there is no redirect for
  Pages). Decide before P1 is published; the base path lives in one place
  (`site.config.mjs`).
- Reference-run noise: run on an otherwise idle machine, report the median of several
  repeats, and record the environment next to the numbers.
- Browser timings differ from native ones; the Results and Discussion must say so.
- The prose is drafted by Claude and edited by the repository owner; the framing of
  the argument is theirs.
